Learn where to repair, propose values on learner states, then score them by solver outcome

The variable-selection GNN stays generic. For the selected variable, a Gaussian proposal head generates candidate values, but it is now trained with DAgger-style learner-visited states so it sees the states its own mistakes create. The final scorer Q(s,i,v) is no longer taught that one stochastic teacher draw is uniquely correct: it learns to rank candidates from their measured one-step improvement in the solver state.

1. Variable selection remains the generic graph problem

The typed GNN embeds variable and constraint nodes and the shared variable head chooses which variable should be repaired. Constraint status is solver state, not a hard-coded chain heuristic. The previous experiment already showed that this branch can learn the violated-endpoint repair decision.

2. Proposal learning now uses learner-visited states

The proposal head still predicts (μ,σ) and learns from demonstrated teacher values. Early training uses clean synthetic states. After a warm-up, an increasing fraction of examples comes from rollouts produced by the current learned proposal/scorer system. This is DAgger-style state aggregation: the value model is explicitly trained on the distribution of states it creates at inference time.

The copied log reports proposal MAE separately on synthetic states and on learner-rollout states, so covariate shift is visible directly.

3. Q(s,i,v) learns what works, not which sample the teacher happened to draw

For a full repair state and selected variable, training generates a pool of candidate values. Each candidate is temporarily applied to the solver state and gets a one-step reward from the change in violated constraints plus a smaller tie-breaking signal from violation magnitude. Those measured rewards are converted into a soft ranking target for the scorer.

This means several different values can all be considered good. The scorer is no longer forced to call 14 correct and 15 wrong merely because one stochastic demonstration happened to sample 14.

Proposal + scorer separation

The proposal answers where should we look? Candidate generation mixes Gaussian samples with generic exploration values such as bounds, current-value perturbations, and random domain samples. The scorer answers which candidate actually improves this solver state? The scorer can therefore become non-Gaussian, multimodal, or highly state-dependent without changing the proposal interface.

Why oracleOutcome matters

If oracleOutcome succeeds while the full model fails, the proposal pool already contains useful values and Q is ranking them badly. If oracleOutcome also fails, the proposal/candidate generator is not placing good values into the pool. Together with oracleValue and oracleVariable, this should isolate the next bottleneck in one run.
